# Оценка узких мест при миграции

## Основные риски

| Приоритет | Проблема | Последствие | Рекомендация |
|---|---|---|---|
| P0 | Один физический сервер / SPOF | Полная недоступность системы | Разнести компоненты, обеспечить резервирование и горизонтальное масштабирование |
| P0 | Big Bang миграция | Длительный downtime и сложный rollback | Выполнять поэтапную миграцию |
| P0 | Неконтролируемая миграция Excel/JPG/PDF | Потеря данных и высокая нагрузка | ETL пакетами, валидация и reconciliation |
| P0 | Нет нагрузочного тестирования | Система не выдержит реальную нагрузку | Провести load/stress tests до cutover |
| P1 | Синхронные цепочки микросервисов | Рост latency и каскадные отказы | Асинхронность, очереди, timeout, Circuit Breaker |
| P1 | Зависимость от лаборатории | Внешний сбой блокирует внутренние процессы | Timeout, retry с backoff, Circuit Breaker |
| P1 | Узкие места БД | Высокий response time | Индексы, connection pooling, анализ запросов |
| P1 | Нет мониторинга и tracing | Медленная диагностика проблем | Метрики, логи, distributed tracing |
| P2 | Недостаток кеширования | Избыточная нагрузка на БД | Добавить кеширование часто читаемых данных |
| P2 | Недостаток опыта команды | Ошибки эксплуатации | Документация, обучение, runbooks |


## Рекомендации

### P0 — до начала промышленной миграции

1. Провести инвентаризацию и очистку исходных данных.
2. Выполнять миграцию поэтапно, а не Big Bang.
3. Реализовать резервирование критичных компонентов.
4. Провести нагрузочное и стресс-тестирование.
5. Подготовить backup и rollback.

### P1 — до переключения пользователей

1. Настроить индексы и connection pools БД.
2. Ограничить длинные синхронные цепочки сервисов.
3. Использовать timeout, retry with backoff и Circuit Breaker для внешних интеграций.
4. Настроить метрики, логи, tracing и alerting.
5. Проверить пропускную способность сети между филиалами.

### P2 — последующая оптимизация

1. Добавить кеширование.
2. Оптимизировать ресурсы сервисов.
3. Настроить autoscaling.
4. Подготовить runbooks и обучение команды.

## Контроль перед миграцией

Перед cutover необходимо проверить:

- p95/p99 latency основных API;
- RPS, соответствующий минимум пятикратному росту;
- CPU, RAM и Disk IOPS;
- количество DB connections;
- error rate;
- время ответа внешних интеграций;
- длительность и пропускную способность процесса миграции данных.
