# Cutover-план миграции

## Выбранная стратегия

Для миграции выбран подход Parallel run.

Во время переходного периода старая и новая системы работают одновременно. Новые процессы постепенно переводятся на новую платформу, при этом старая система некоторое время остаётся доступной как резервный вариант.

Для «Медикаменте» этот подход подходит по следующим причинам:

- текущие данные распределены между Excel и файлами;
- медицинские и персональные данные критичны, поэтому потеря информации недопустима;
- новая система внедряется одновременно с изменением бизнес-процессов;
- можно сравнивать данные старой и новой систем перед окончательным переключением;
- при проблемах можно временно продолжить работу на старой системе.

Основные недостатки подхода:

- необходимость временно поддерживать две системы;
- необходимость синхронизировать данные между Legacy и To-Be;
- увеличение сложности эксплуатации на переходном этапе;
- риск появления расхождений между системами.

## Cutover-план

| Этап | Описание действия | Ключевые задачи | Ответственные | Срок | Риски и меры по снижению |
|---|---|---|---|---|---|
| 1. Инвентаризация | Определить все источники и владельцев данных | Excel, JPG/PDF, 1С, журналы, медицинские данные; определить Golden Source | Архитектор, бизнес-аналитик | 1 неделя | Пропущенный источник данных → сверка с подразделениями |
| 2. Подготовка данных | Очистить данные перед переносом | Удаление дублей, проверка форматов, обязательных полей и связей | Бизнес-аналитик, разработчики | 1–2 недели | Некорректные данные → validation report и ручная проверка ошибок |
| 3. Backup | Создать резервную копию текущего состояния | Backup файлов, Excel, 1С и конфигураций | Администратор | Перед миграцией | Потеря данных → проверить возможность восстановления из backup |
| 4. Развёртывание To-Be | Подготовить новую платформу | CRM, БД, API Gateway, IAM, мониторинг | DevOps, разработчики | 1 неделя | Ошибочная конфигурация → предварительное тестирование на staging |
| 5. Initial migration | Выполнить первоначальную загрузку данных | ETL из Legacy в новую систему | Разработчики, DBA | 1–2 дня | Высокая нагрузка → пакетная миграция и ограничение размера batch |
| 6. Проверка данных | Сравнить Legacy и To-Be | Количество записей, контрольные суммы, бизнес-проверки | BA, QA, DBA | 1–2 дня | Расхождения → исправление ETL и повторная загрузка |
| 7. Parallel run | Запустить обе системы одновременно | Новая система используется пилотными пользователями, Legacy остаётся доступной | Все команды | 2–4 недели | Расхождение данных → синхронизация и reconciliation |
| 8. Pilot | Перевести ограниченную группу пользователей | Например, часть сотрудников ресепшена и врачей | BA, QA, пользователи | 1 неделя | Критические ошибки → возврат pilot-группы в Legacy |
| 9. Расширение нагрузки | Постепенно переводить остальных пользователей | Перевод 10% → 30% → 50% → 100% пользователей | Архитектор, DevOps | 1–2 недели | Рост ошибок или latency → остановить увеличение нагрузки |
| 10. Финальная синхронизация | Перед отключением Legacy перенести последние изменения | Delta migration, reconciliation | DBA, разработчики | Несколько часов | Потеря последних изменений → повторная delta migration |
| 11. Cutover | Сделать новую систему основной | Legacy перевести в read-only | Архитектор, DevOps | Плановое окно | Критическая ошибка → rollback на Legacy |
| 12. Monitoring | Усиленно контролировать новую систему | Error rate, latency, БД, интеграции, бизнес-метрики | DevOps, разработчики | 1–2 недели | Незамеченные проблемы → alerts и дежурство команды |
| 13. Decommission | Вывести Legacy из эксплуатации | Архивировать данные и отключить старые компоненты | Архитектор, администратор | После стабилизации | Слишком раннее отключение → grace period 2–4 недели |

## Основные риски

| Приоритет | Риск                                           | Мера по снижению                               |
| --------- | ---------------------------------------------- | ---------------------------------------------- |
| P0        | Расхождение данных Legacy и To-Be              | CDC/ETL + автоматический reconciliation        |
| P0        | Потеря изменений во время Cutover              | Final delta migration перед переключением      |
| P0        | Повреждение или потеря данных                  | Backup + проверенный restore                   |
| P0        | Критический дефект новой системы               | Возможность быстрого rollback                  |
| P1        | Ошибка миграции данных                         | Validation, контрольные суммы, бизнес-проверки |
| P1        | Недостаточная производительность To-Be         | Load и stress testing до Cutover               |
| P1        | Сбой лаборатории или 1С                        | Timeout, Retry with Backoff, Circuit Breaker   |
| P1        | Ошибка синхронизации                           | DLQ/журнал ошибок и повторная обработка        |
| P2        | Пользователи продолжают работать в Legacy      | После Cutover перевести Legacy в read-only     |
| P2        | Ошибки сотрудников при переходе                | Pilot, инструкции и обучение                   |

## Распределение ответственности
| Роль                              | Ответственность                                                         |
| --------------------------------- | ----------------------------------------------------------------------- |
| Технический директор / архитектор | Общая координация миграции, решение о начале этапов и финальном Cutover |
| Администратор / DevOps            | Инфраструктура, backup, monitoring, переключение и rollback             |
| Разработчики                      | ETL, CDC, синхронизация, исправление ошибок. Перенос БД, reconciliation, backup и restore                             |
| QA                                | Functional, integration, regression и load testing                      |
| Бизнес-аналитик                   | Проверка корректности бизнес-данных и сценариев                         |
| Support / Operations              | Контроль состояния системы после Cutover                                |

## План отката

До завершения Parallel run старая система не удаляется и остаётся доступной для возможного возврата.

При критической проблеме выполняются следующие действия:

1. Остановить дальнейшее увеличение нагрузки на To-Be.
2. Определить изменения, выполненные после последней успешной синхронизации.
3. Синхронизировать необходимые изменения обратно в Legacy.
4. Выполнить reconciliation данных.
5. Переключить пользователей обратно на Legacy.
6. Провести анализ причины проблемы.
7. Исправить ошибку.
9. Провести повторное тестирование.
10. Повторить этап Parallel run.

Rollback выполняется при следующих условиях:

* потеря или повреждение данных;
* невозможность регистрации или записи пациента;
* невозможность доступа врача к медицинским данным;
* критический сбой оплаты;
* массовые ошибки синхронизации;
* длительная недоступность основных функций;
* нарушение корректности разграничения доступа.
